## 一、KV-Cache 基础概念

KV Cache（Key-Value Cache）是 Transformer 大模型推理加速的核心机制：

- **原理**：自回归生成时，每生成一个新 token 都需要 attention 到之前所有 token。KV Cache 把已计算过的 Key/Value 张量缓存起来，避免每一步都重复计算历史 token
- **效果**：没有 KV Cache，推理速度会慢 100 倍以上
- **代价**：上下文越长，KV Cache 占用的显存越大（通常是推理显存瓶颈）

厂商的 KV-Cache 策略可分为三个层面：
1. **推理层**：底层 KV Cache 的存储格式与压缩（MLA、GQA、MQA 等）
2. **缓存层**：Prefix Cache / Prompt Cache 的命中策略
3. **计费层**：缓存命中的折扣定价

## 三、各厂商深度分析

### 3.1 DeepSeek —— 磁盘缓存 + MLA 压缩

**来源**：https://api-docs.deepseek.com/zh-cn/guides/kv_cache

#### 核心机制

DeepSeek 的 KV Cache 通过 **Multi-head Latent Attention (MLA)** 架构实现大幅压缩，将 KV Cache 缩小约 4 倍，使其可以经济地存储到磁盘 SSD。

#### 缓存落盘规则

三种触发时机：
1. **请求结束位置落盘**：每次请求的用户输入结束位置与模型输出结束位置，各产生一个缓存前缀单元
2. **公共前缀检测落盘**：系统检测到多次请求之间存在公共前缀时，将该公共前缀独立落盘
3. **按固定 token 间隔落盘**：长输入/长输出中，按固定 token 数量截取缓存前缀单元

#### 命中规则

缓存前缀是一个独立的完整单元。后续请求**必须完整匹配**缓存前缀单元才能命中。受 Sliding Window Attention 机制影响，存取与判别有所不同。

示例：
- 第一次请求 A+B，第二次请求 A+B+C → 命中 A+B 缓存 ✅
- 第一次请求 A+B，第二次请求 A+C → 不命中 A+B，但系统识别到公共前缀 A 并落盘
- 第三次请求 A+D → 命中 A 的缓存 ✅

#### API 使用

- **无需修改代码**：对所有用户默认开启
- **查看命中情况**：API 返回中增加两个字段
  - `prompt_cache_hit_tokens`
  - `prompt_cache_miss_tokens`
- **输出不受影响**：只匹配输入前缀，输出仍然计算推理，受 temperature 影响

#### 关键特征
- 最小匹配粒度：**64 tokens（业界最细）**—— 小范围 prompt 修改仍能命中大部分缓存
- TTL：**数小时到数天** —— 远长于其他厂商
- 缓存构建时间：秒级
- 缓存自动清空：不再使用后数小时到几天

#### 实测数据（2026-05-25, ~7K 前缀）

| 指标 | 数值 |
|------|------|
| 未命中成本 | $0.00091 |
| 命中成本 | $0.00023（-74%） |
| 命中率 | 96%（6,784/7,101） |
| 命中 TTFT | 2.93 秒 |
| 未命中 TTFT | ~4.0 秒 |

#### 优劣势

✅ **优势**：
- 磁盘持久化，缓存寿命长
- 64 token 细粒度匹配
- 自动生效，零改代码
- 中文场景低价高效，缓存命中率可达 98%

❌ **劣势**：
- 仅限自家模型
- 英文推理质量落后 Claude/GPT-5
- 未命中时延迟较高（~4s）

### 3.2 Anthropic Claude —— 显式断点缓存

#### 核心机制

开发者通过 `cache_control` 标记手动指定哪些消息块需要缓存。最多可设置 4 个断点，实现分层缓存。

#### API 使用

```python
{
  "role": "system",
  "content": [
    {
      "type": "text",
      "text": "你是一位乐于助人的助手...",
      "cache_control": {"type": "ephemeral"}
    }
  ]
}
```

#### 关键特征
- 最小缓存块：1,024 tokens
- TTL：5 分钟滑动（默认）或 1 小时
- 写入需付费（输入价的 125% 或 200%）
- 读取仅需输入价 10%
- 不支持隐式回退 —— 忘记加标记就没有缓存

#### 实测数据（2026-05-25, ~7K 前缀）

| 模型 | 未命中 TTFT | 命中 TTFT | 加速 |
|------|-----------|----------|------|
| claude-haiku-4-5 | ~3.0s | 1.31s | ~2× |
| claude-sonnet-4-5 | ~2.0s | 1.76s | ~1.2× |
| claude-opus-4-5 | ~2.2s | 2.08s | ~1.05× |

#### 优劣势

✅ **优势**：
- 最高控制力（4 个独立断点）
- 最深度折扣（90% off）
- 长上下文 Agent 和多轮对话表现出色

❌ **劣势**：
- 需手动修改代码
- 5 分钟默认 TTL 对突发任务不友好
- 哈希对顺序敏感
- 网关兼容性问题（OpenAI 兼容路径不支持 cache_control）

### 3.3 OpenAI GPT-5 —— 自动内存缓存

#### 核心机制

完全自动的前缀缓存，无需任何代码改动。当请求前缀 ≥ 1,024 tokens 且与近期请求匹配时自动生效。

#### 关键特征
- 最小匹配：1,024 tokens，增量步长 128 tokens
- TTL：约 5-60 分钟
- 写入免费
- 命中折扣 50%
- 无法强制命中

#### 实测数据（2026-05-25, ~7K 前缀）

| 模型 | 未命中成本 | 命中成本 | 命中率 | 命中 TTFT |
|------|-----------|---------|-------|----------|
| gpt-5.4-nano | $0.00131 | $0.00074（-44%） | 85% | 1.00s |
| gpt-5.4-mini | $0.00267 | $0.00257* | 93% | 0.73s |

#### 优劣势

✅ **优势**：
- 零代码改动
- 与 DeepSeek API 格式兼容，迁移成本低

❌ **劣势**：
- 折扣最浅（仅 50%）
- 无法控制/强制命中
- 突发流量下 TTL 不确定

### 3.4 Google Gemini —— 混合模式

#### 核心机制

两种模式：
1. **隐式**：自动匹配，类似 GPT-5，折扣 ~75%
2. **显式**：通过 CachedContent API 创建缓存对象，开发者设置 TTL，按小时付存储费

#### 关键特征
- 显式模式：最小 32K tokens（早期模型）/ 更低（新模型）
- TTL：隐式数分钟；显式自定义（默认 1 小时，最长 24 小时）
- 显式模式读价 ~10%，需付存储费
- 缓存对象与区域绑定

#### 实测数据（2026-05-25, ~7K 前缀）

| 模型 | 未命中成本 | 命中成本 | 命中率 |
|------|-----------|---------|-------|
| gemini-2.5-flash | $0.00198 | $0.00024（-88%） | 97% |
| gemini-2.5-pro | $0.00824 | $0.00205（-75%） | 84% |

#### 优劣势

✅ **优势**：
- 显式模式 24 小时 TTL，适合长时间跨度的文档问答
- 隐式也有 ~75% 折扣
- 长上下文处理能力强

❌ **劣势**：
- 显式模式需两步流程（创建→引用），增加代码复杂度
- 存储费对低频调用不划算
- 缓存区域绑定，多区域部署需重复缓存

## 五、Prompt 优化最佳实践

### 5.1 Prompt 顺序编排

KV Cache 只匹配前缀，**prompt 必须按从最稳定到最变化的顺序排列**：

```
✅ 正确顺序：
system prompt（不变） → tool definitions（少变） → 检索上下文 → user message（多变）

❌ 错误顺序：
user message → system prompt → tool definitions → 检索上下文
```

### 5.2 值得缓存的 Prompt 类型

1. **长系统提示词** —— 最稳定、收益最大
2. **检索上下文** —— 会话内稳定的文档/代码库
3. **Few-shot 示例** —— 分类/抽取任务的不变示例
4. **工具定义** —— 10+ 个工具的 JSON Schema
5. **对话历史** —— 长会话中累积的历史
6. **多文档 RAG** —— 每次加载相同的大型参考文档

### 5.3 缓存命中率指标

健康的 Agent 应用通常达到 **60-90%** 缓存命中率。低于 **30%** 通常意味着 prompt 中有随机变量（时间戳、随机 ID）侵入了缓存区域。

## 六、底层架构演进

### 注意力头压缩技术

| 技术 | 提出者 | KV Cache 缩放 | 说明 |
|------|--------|-------------|------|
| MHA（Multi-Head Attention） | 原始 Transformer | 1× | 每个注意力头独立存储 KV |
| MQA（Multi-Query Attention） | Google | ~1/8× | 所有 query 头共享一组 KV |
| GQA（Grouped Query Attention） | Google | 1/2~1/8× | query 头分组共享 KV |
| **MLA（Multi-head Latent Attention）** | **DeepSeek** | **~1/4×** | KV 投影到低维潜空间，大幅压缩 |

MLA 是 DeepSeek 实现磁盘缓存的**关键技术基础**，将 KV Cache 压缩到可在 SSD 上经济存储的体积。

### 推理框架中的 KV Cache 管理演进

1. **连续缓存**（早期）—— 预分配固定大小显存，碎片化严重
2. **PagedAttention**（vLLM）—— 分页式管理，类似虚拟内存
3. **异构缓存** —— GPU + CPU + SSD 多层存储
4. **统一内存架构** —— 单地址空间管理所有缓存层次
