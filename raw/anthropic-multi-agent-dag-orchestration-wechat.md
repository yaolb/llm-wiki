# Anthropic 提出一种新的多 Agent 编排方式

FIELD NOTES

Agent 可以离开，可以换人；任务状态必须留下来。

Anthropic 在9 月 4 日公开了一个非常夸张的多 Agent 实验：几十个 Claude Agent 在 Lean 4（一种能把数学证明写成代码，并让计算机检查推导是否正确的编程语言和证明工具） 中协作，用 11 天生成约 1300 万行 Lean 代码、证明了 30,300 个中间定理，其中 29,500 个进入最终证明，完成了费马大定理的端到端机器验证。

Anthropic 在这个项目中遇到过一个问题：Agent 能完成局部证明，但是放到一起后，却丢失了项目进度，协作也随之失效。后来，团队接入 Prove2Me（本文的多Agent协作平台），用定理依赖图（DAG）组织工作，才完成了这次任务。Anthropic 官方文章

这段经历比「如何启动几十个 Agent」更值得讨论。一个 Agent 写完的东西，另一个 Agent 要从哪里找？它能不能用？还有哪些前提没解决？这些问题如果靠主 Agent 在对话里记忆和转述，就会导致项目越大，交接越难。

— Anthropic 官方文章封面。来源：Anthropic。

我想从这次项目中借鉴的，是一种围绕任务及其依赖组织 Agent 的方法。Agent 可以离开，可以换人，工作记录和验收结果留在系统中，后来的 Agent 能接着做。

要理解它，得先看清 DAG 中的节点和连线各自表示什么。

## 01 TASK CONTRACT — DAG 里存的，是要交付的结果

DAG 的中文名是「有向无环图」。在这个项目里，节点表示定理，连线记录证明对其他定理的依赖。假如目标 T 需要 A 和 B，图里就要保留这层关系；A 如果还依赖 C，就继续往下展开。同一个结论可能被多个证明引用，所以整张图未必是一棵树。

「无环」约束也有具体含义：不能用 A 证明 B，再用 B 证明 A，把一圈尚未成立的结论当作证明。

这与给 Agent 分配角色有区别。「负责分析」「负责写代码」描述的是分工，但没有说交出什么才算完成。定理节点则有一份形式化声明，写明条件和结论。无论哪位 Agent 接手，都面对同一个目标。

Prove2Me 把声明与证明分开保存。声明固定下来后，可以有多个证明；某个 Agent 尝试失败，不需要把目标也换掉。

类比到软件开发中，可以把节点写成「切换账号后，旧请求不能更新新会话的数据」，而不是「检查登录模块」。前者给出了行为约束，也留下了选择实现的空间。取消请求、校验会话版本，或者修改缓存写入位置，都可以作为候选方案，接受同一组验收。

图中的每条边也要有依据。任务 A 排在任务 B 前面，不代表 B 依赖 A。只有 B 要使用 A 的结果，才需要记录这条依赖。否则，原本能并行的工作会被排成串行。

— Anthropic 公布的部分证明里程碑。图中展示了不同分支如何汇入目标，不包含全部定理节点。来源：Anthropic。

## 02 PROOF SKETCH — 子任务没完成，父任务也能往前做

一张依赖图如果只用来回答「谁先做、谁后做」，还解释不了 Prove2Me 的协作方式。

它允许 Agent 提交 proof-sketch。这个词可以译成「证明草图」，但这里的草图是能接受检查的代码，不是一段「接下来应该这样做」的计划。它可以引用尚未证明的子定理，先建立一条有条件的推导：只要这些子定理成立，目标就成立。Prove2Me 论文，第 4.2 节

用 T、A、B 举个教学例子。Agent 甲想证明 T，发现自己需要 A 和 B。它可以先把 A、B 登记成待解决的目标，再写出从 A、B 推到 T 的证明，交给平台检查。

检查通过，意味着这条推导成立。A、B 仍然欠着。

平台的公开文档用 SKETCH_ACCEPTED 表示这种提交：推导通过检查，但引用了未完成的定理。等这份推导所需的子定理全部被证明，父目标才能转为 Proved。因此，「方案成立」和「工作完成」是两个状态。Prove2Me 提交与验证文档

— 证明草图如何连接并行工作。图中 T、A、B 是教学示例，不是费马大定理项目中的具体节点。

Agent 乙可以接手 A，Agent 丙去处理 B。甲不需要把自己的整段对话发给它们，只需要让它们读到对应声明、定义和相关资料。甲也可以换一个分解方案，尝试通过 D 推出 T。

这时，T 会有两条候选路线：一条需要 A 和 B，另一条需要 D。编排系统应把依赖归属于各自的方案，不能把 A、B、D 混成一张必须全部完成的清单。Prove2Me 允许一个声明拥有多个证明，这也提醒我们：任务图除了节点状态，还需要记录「哪个方案依赖哪些结果」。

这种协作把一部分等待变成了可交接的工作。有人搭建整体推导，有人补子结论，工作可以在不同层次展开。对编排者而言，分解本身也是一种产物，需要说明子任务完成后如何支撑父目标。

## 03 SCHEDULING — Agent 从哪里找到下一项工作

接下来是调度问题。几万个节点放在一张图上，Agent 仍然需要一个入口。

Prove2Me 的公开 solver 文档要求 Agent 从任务的里程碑入手，再查看未解决的叶子节点，也就是当前可继续展开或求解的工作。动手前，还要读已有分解、失败尝试和讨论记录。文档提供了查询依赖图和未完成叶子的接口。Prove2Me Solver 文档

这里的里程碑负责给工作定方向。只让 Agent 在整张图里挑任务，可能出现一种情况：完成数量不断增长，主目标却没推进，因为大家都在做容易解决、与当前阻塞无关的节点。

例如，一个代码修复任务卡在「无法复现」，此时让更多 Agent 优化实现细节，未必有用。调度者需要知道，复现结果会影响哪条修复路线，哪些任务正在等它。依赖图提供这部分信息，优先级策略再决定把资源分给谁。

公开资料支持的是按里程碑、依赖和未完成节点组织工作，不能据此断言 Anthropic 使用了某种最优调度算法。如果在自己的系统里按「能解除多少阻塞」排序，那是一个可测试的工程选择，仍要结合任务难度和成本评估。

复用也需要进入工作流程。Prove2Me 的论文说明，平台为定理保存自然语言描述并提供检索，要求 Agent 在新增定理前搜索已有结果。Prove2Me 论文，第 4.3 节

查到名称相近的结果，还不够。假设别人证明了「单线程下不会重复写入」，当前任务要处理并发请求，就不能把这个结果接过来。自然语言用于找到候选项，正式条件决定它是否适用。

对工程 Agent，我会把搜索已有产物放到领取任务之后、生成方案之前。失败记录也应可查：哪条路径试过，基于哪个版本，为什么没继续。这样，Agent 重启后可以恢复调查，不必重走别人放弃的路。

## 04 STATE & VERIFY — 图要能维护，完成状态要有依据

Agent 越多，越容易出现「同名任务，条件不同」的问题。一位 Agent 修改目标，另一位仍按旧条件工作，结果即使各自通过检查，也可能接不上。

Prove2Me 的公开贡献文档允许修改自然语言说明、来源和标签，不开放形式化声明等字段的修改。需要改变目标时，应发布新条目。这让引用者有办法知道自己依赖的到底是哪一个声明。Prove2Me 贡献文档

声明与证明分离也能减少修改带来的构建负担。Anthropic 将这一点列为 Prove2Me 帮助项目推进的原因之一。Anthropic 官方文章

在公开的费马大定理仓库中，这种分离体现在目录上：Theorems/ 放声明，P2M/Sol/ 放证明，Definitions/ 放定义。证明文件引用了哪些定理，可以从它的 import 关系中追踪。仓库说明、依赖文档说明

这比把全部工作塞进共享文件更容易交接，但它还需要验证器。Agent 写下「完成」，只能算一次报告；系统要检查产物是否满足目标，才能让下游使用。

数学形式化在这里有一个优势：Lean 可以检查证明是否符合声明。费马项目还报告了 Comparator 对目标与定义的核对，以及独立 Lean 内核 nanoda 的检查。仓库验证说明

软件开发没有同等通用的验收手段。一组测试通过，不能保证所有输入下都正确；如果 Agent 为了通过检查删掉了断言，绿色报告甚至可能掩盖退步。因此，把这套方法用于代码修复时，验收条件和检查程序应独立管理，修改它们需要留下理由和审核记录。

这里还有一条边界：平台当前的公开工作流能帮助解释机制，但不等于 Anthropic 当时内部 harness 的完整实现。不能把自己补上的锁、队列和重试策略，写成那次实验已经公开的设计。

## 05 ORCHESTRATION — 把这套方法用到自己的 Agent 系统

如果让我据此编排一个代码修复系统，我会从一个能复现的问题开始，而不是先决定设几个 Agent 角色。下面以「退出登录后，旧请求污染新账号数据」为假设场景，说明怎么组织工作。

先写验收场景：旧账号的请求还在途中，用户退出并登录新账号；旧响应返回时，不能改变新会话的界面与缓存。这是主目标，调查和修复都围绕它展开。

然后拆出两个可以并行的调查任务：一个构造这段请求时序并复现污染，另一个追踪响应从网络层到缓存、界面的写入路径。它们交出的应是复现代码、调用位置和日志，而不只是「问题可能出在缓存」的总结。

修复 Agent 可以先提出带前提的方案，例如「在所有写入点校验会话标识」。但它必须列出尚未确认的前提：是否找全了写入点，会话标识何时变化，缓存是否存在绕过校验的入口。调查结果回来后，再判断这个方案是否站得住。

这借用了 proof-sketch 的工作方式，却没有数学上的组合保证。方案通过评审，只能表示值得继续实现，最终仍要在目标代码版本上运行验收。

— 面向代码修复的编排示意。此图是本文的工程建议，不是 Anthropic 内部架构。

要让这个过程跨会话运行，任务至少需要保存下面这些内容。下面的字段名只是示例，不是 Prove2Me 的数据结构。

| 保存什么 | 用来解决什么问题 |
|---|---|
| 目标与验收条件 | 接手者知道要交付什么 |
| 所属方案与依赖 ID | 知道哪个方案在等待哪些结果 |
| 输入版本、产物地址 | 代码改动后能追溯结果是否过期 |
| 验证记录 | 区分提交、通过检查和最终验收 |
| 失败原因、后续线索 | 换一个 Agent 后能继续调查 |

Worker 的一次工作，可以围绕这条过程展开：读取目标，检查已有结果，领取任务，提交产物或分解方案，等待验证，再选下一项工作。主 Agent 可以保留规划与审查职责，但不必充当每一次结果交接的中转站。

并发领取需要原子操作，否则两个 Worker 会把同一个任务都当成自己的。领取记录还要有期限；Worker 中断后可以回收任务，恢复运行的旧 Worker 则不能覆盖新提交。这些是实现共享任务系统时要补的机制，DAG 本身不提供它们。

依赖更新也一样。上游产物变了，下游旧的验收记录不能继续沿用。可以让验证结果绑定输入版本或内容哈希，重新检查受影响的分支。对于互相影响的代码改动，如果无法拆出清楚的契约，就把它们放进同一个集成任务，不要为了画成 DAG 硬拆。

我会在这个规模上验证系统是否值得扩展：两个 Worker、一个有依赖的修复目标，运行中中断其中一个 Worker，换一个接手。看它能否找回输入、理解未完成的前提，并提交可验收的结果。

如果任务只是让几个 Agent 各写一份独立评审，最后由人阅读，那么让主 Agent 分发再汇总就够了。对于需要跨会话、复用中间产物、多人接力的工作，我更倾向于让任务状态保存在系统中，让 Agent 围绕这些记录工作。
