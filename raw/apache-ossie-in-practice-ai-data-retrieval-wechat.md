# Apache Ossie 实战：我如何给 AI 取数系统搭一层业务语义地基

大家好，我是胡二。
上一篇写 Apache Ossie，我更多是在讲一件事：AI 时代，语义层为什么需要一个开放交换标准。
这篇想往前走一步。
不再只讲「为什么」，而是讲「怎么用」。
我最近在做 AI 取数、AI 报表一类系统时，越来越强烈地感受到一个问题：真正难的不是让大模型写 SQL，而是让它知道这家公司里的数据到底是什么意思。
一个完整的 AI 取数链路，大概是这样：
用户问题 -> 找表 -> 生成 SQL -> 取数 -> 代码二次处理 -> 可视化
看起来很顺。
但真正进入生产环境之后，最难的地方往往卡在前两步：
从一万多张表里找到正确的表。
基于正确的业务口径生成准确的 SQL。
而且这里的「准确」，不是语法正确这么简单。
它还要知道事实表和指标表怎么选，知道指标之间的依赖关系，知道哪些字段不能直接加总，知道某些业务线有特殊过滤逻辑，知道用户口中的黑话应该映射到哪个内部字段。
如果这些语义只散落在 Wiki、字段注释、历史 SQL、分析师经验和 BI 配置里，AI 就很容易写出一种最危险的 SQL：
看起来很合理，跑起来也有结果，但业务口径是错的。
所以我现在更倾向于把 AI 取数系统背后的业务语义知识库拆成三层：
Ossie 负责结构化语义。
Wiki 负责业务解释和例外说明。
图 + 向量库负责对象关系和反向映射。
这三层叠起来，才像是一套真正能让 AI 使用的业务语义知识库。

一、先别急着让模型写 SQL
很多 AI 取数系统的第一版，都会从 Text-to-SQL 开始。
用户问一句：
「看一下上个月华东区新用户贡献的收入。」
系统把库表结构塞给模型，模型生成 SQL，然后执行。
在 demo 场景里，这条路很容易跑通。
因为 demo 通常只有几十张表，字段名比较干净，业务口径也比较简单。
但真实企业环境不是这样。
真实环境里，可能有 Hive、StarRocks、PostgreSQL 等多套数据库；同一个业务对象可能在不同系统里有多张表；历史原因留下来的字段名可能非常抽象；有些表是明细事实表，有些表是宽表，有些表是指标汇总表；还有一些字段看起来像金额，但实际只是中间计算字段。
这时如果让模型直接「猜表 + 猜字段 + 猜口径」，风险会非常高。
比如用户问「收入」。
模型可能去事实表里 sum 支付金额。
也可能去指标表里取已经加工好的收入指标。
还可能把 GMV、实收金额、净收入、确认收入混在一起。
如果系统里有多个指标同时存在，模型不仅要知道每个指标怎么算，还要知道指标之间的层级关系：
事实表里有什么原始字段。
哪些原始字段可以形成原子指标。
哪些原子指标进一步派生出业务指标。
哪些业务指标又组合成衍生指标。
这就是 Ossie 能开始发挥作用的地方。
它不是替模型写 SQL，而是先把「什么是数据集、什么是字段、什么是指标、它们之间怎么关联」变成机器可读的语义模型。
二、Ossie 在实战里解决的第一件事：让表和指标不再混乱
上一篇说过，Apache Ossie 的定位不是一个新的 BI 工具，而是一个开放的语义模型交换标准。
它用 JSON / YAML 这样的格式描述语义模型，让不同数据平台、BI 工具、AI Agent 能够交换和使用同一套语义定义。
官方仓库里对它的描述也很直接：Ossie 是一个面向 analytics、AI 和 BI 生态的 vendor-agnostic semantic model specification，目标是减少不同工具之间语义元数据不一致的问题。
放到 AI 取数场景里，我最看重的是这几类对象：
Dataset：业务数据集，通常对应事实表、维表、宽表或逻辑查询。
Field：数据集里的字段，包括字段类型、表达式、是否是时间维度等。
Relationship：数据集之间的关联关系，比如订单表和用户表怎么 join。
Metric：业务指标，比如支付金额、净收入、复购率、客单价。
AI Context：给模型看的业务说明、同义词、使用指令和示例问题。
Custom Extensions：保留内部平台或厂商特有的信息。
这些对象组合起来，就能把原来散在不同系统里的语义收拢到一个结构化模型里。
比如在没有 Ossie 之前，AI 面对「订单收入」时可能只看到一堆表：
dwd_order_detail
dws_order_summary_day
ads_revenue_dashboard
metric_finance_income_day
如果字段注释不完整，模型很难判断该用哪张。
引入 Ossie 之后，我们可以把链路表达得更清楚：
事实表：订单明细。
原子指标：支付金额、退款金额、优惠金额。
派生指标：净支付金额、有效订单数。
衍生指标：客单价、复购率、收入贡献。
可用维度：日期、地区、渠道、用户类型、商品类目。
推荐数据集：在某些高频分析场景里优先使用已治理的汇总表。
这样模型不再只是在表名里猜意思，而是在一个结构化语义空间里选择对象。
更重要的是，Ossie 可以把 Hive、StarRocks、PostgreSQL 等不同数据库里的语义统一到一套标准描述中。
底层存储可以不同，SQL 方言可以不同，物理表可以分散，但在 AI 取数系统看来，它面对的是一套相对稳定的业务语义模型。
这一步很关键。
因为 AI 最怕的不是不知道，而是不知道自己不知道。
当表、字段、指标、关系都有明确结构，模型至少可以在边界内工作；遇到语义缺失时，也更容易暴露出来，而不是偷偷编一个答案。

三、但 Ossie 不是全部，Wiki 仍然很重要
如果只看结构化语义，Ossie 很适合。
但真实业务里有很多东西，并不适合全部塞进 Ossie。
比如：
业务领域怎么划分。
某个业务概念为什么这么定义。
某些历史口径为什么调整过。
某些特殊逻辑什么时候启用。
数据标准背后的治理规则。
内部用户 ID 的命名和识别规则。
不同部门使用同一个词时的语言习惯差异。
历史问句里沉淀下来的业务理解。
这些内容通常有背景、有争议、有演进过程，也经常需要用自然语言解释。
它们更适合放在 Wiki、指标文档、数据标准文档或业务知识库里。
所以我不会把 Ossie 和 Wiki 看成替代关系。
Ossie 负责「结构化、可执行、可交换」。
Wiki 负责「解释、背景、例外、决策过程」。
举个例子。
「有效用户数」这个指标，在 Ossie 里可以定义 metric 表达式，声明使用哪个数据集、哪个时间字段、哪些维度可用、有哪些同义词。
但为什么要排除内部账号？
内部账号有哪些识别规则？
某些测试部门的账号是否也要排除？
2025 年之前和之后的规则有没有差异？
这些东西放在 Wiki 里更自然。
AI 取数系统在生成 SQL 时，先从 Ossie 拿结构化对象，再从 Wiki 拿业务解释和例外规则。
前者告诉它「应该查什么」。
后者告诉它「为什么要这样查，以及哪些坑不能踩」。
四、图 + 向量库补的是「关系」和「反向映射」
除了 Ossie 和 Wiki，我还会引入图 + 向量库。
原因也很简单：AI 取数里的很多问题，本质上不是文本检索问题，而是关系推理问题。
用户说的词，未必正好是字段名。
用户说的值，未必正好是数据库里的枚举值。
用户问的指标，未必直接落在一张表里。
比如用户问：
「帮我看一下小红书渠道最近一周的新客收入。」
系统需要解决一串映射：
「小红书」对应哪个渠道枚举值？
这个枚举值在哪些表的哪个字段里出现？
「新客」应该用用户首购时间判断，还是用注册时间判断？
「收入」对应哪个指标？
这个指标可以按渠道和新老客同时拆分吗？
如果要关联用户表、订单表、渠道表，推荐 join 路径是什么？
这类关系用普通文档很难稳定表达。
图 + 向量库更适合承载这些对象之间的连接：
字段值 -> 字段。
字段 -> 表。
表 -> 表。
表 -> 指标。
指标 -> 指标。
业务词 -> 字段值。
历史问句 -> SQL 模板。
报表 -> 指标。
当用户输入一个自然语言问题时，系统可以先做多路召回：
从 Ossie 找相关 dataset、field、metric、relationship。
从 Wiki 找相关业务解释、特殊逻辑、数据标准。
从图 + 向量库沿着对象关系扩展候选表、候选字段、候选指标和候选枚举值。
从历史问句库找相似问题和已验证 SQL。
然后再把这些结果合并、排序，交给模型生成 SQL。
这时模型拿到的就不是一堆散乱片段，而是一组有结构的候选路径。
它可以知道：
这个问题可能对应哪些指标。
每个指标依赖哪些表和字段。
哪些表之间可以 join。
哪些字段值需要做同义词映射。
历史上类似问题是怎么写 SQL 的。
这样 AI 取数才从「让模型凭感觉写 SQL」，变成「让模型在语义约束下组装查询计划」。

五、一个更可靠的 AI 取数流程
把这些东西合起来，我现在更认可的流程是：
第一步，理解用户问题。
识别时间范围、业务对象、指标、维度、过滤条件、输出形式，以及是否需要图表或二次分析。
第二步，召回结构化语义。
从 Ossie 中找 dataset、field、metric、relationship，尤其关注指标依赖、时间字段、可用维度和 SQL 方言。
第三步，召回业务知识。
从 Wiki 或知识库中找概念定义、特殊口径、数据标准、内部规则、历史变更说明。
第四步，做关系扩展。
用图 + 向量库补齐字段值到字段、字段到表、表到指标、表到表之间的关系，处理用户语言和系统字段之间的反向映射。
第五步，生成 SQL。
让模型基于候选语义对象生成 SQL，而不是从全库表结构里自由发挥。
第六步，执行取数。
根据数据库类型选择执行引擎，比如 Hive、StarRocks 或 PostgreSQL。
第七步，代码二次处理。
有些结果不适合直接 SQL 完成，比如复杂排序、分桶、同比环比计算、异常点识别、图表数据整理，可以交给代码处理。
第八步，可视化和解释。
输出图表、表格和自然语言解释，同时保留 SQL、指标口径和数据来源，方便用户追溯。
这条链路里，Ossie 不是唯一核心，但它是一个很重要的中间层。
没有它，系统很容易退回到「表结构 + Prompt + RAG 片段」。
有了它，业务语义开始有了一个可版本化、可校验、可交换的结构化载体。
六、验证比生成更重要
AI 取数系统里，生成 SQL 只是开始。
真正决定能不能上线的是验证。
我一般会把验证拆成四类。
第一类，SQL 逻辑验证。
检查表是否存在、字段是否存在、join 关系是否合理、聚合层级是否正确、时间字段是否选对、过滤条件是否遗漏。
这里可以充分利用 Ossie 里的 dataset、field、relationship 和 metric 定义。
如果某个 metric 明确依赖订单支付时间，模型却用了订单创建时间，就应该被拦下来。
第二类，强业务规则验证。
有些规则不是 SQL 语法能看出来的。
比如内部账号必须排除。
测试门店必须排除。
某类退款订单不能进入收入。
某些业务线只能使用特定汇总表。
这些规则可以来自 Wiki、数据标准文档，也可以沉淀成专门的校验器。
第三类，数据量级验证。
SQL 能跑出来，不代表结果可信。
如果一个日活指标突然比历史均值大十倍，或者一个收入指标比财务报表差两个数量级，系统需要给出风险提示。
这类验证不一定能判断绝对对错，但能发现明显异常。
第四类，历史问句对比。
对高频问题，应该维护一批已验证问句和 SQL。
当用户提出类似问题时，新生成的 SQL 可以和历史执行逻辑做比对。
它不要求完全一样，但至少要解释差异：
为什么这次用了另一张表？
为什么过滤条件变了？
为什么时间字段不同？
为什么指标口径更新了？
这个环节非常重要。
因为 AI 系统的质量，不应该只靠一次回答的表面效果来判断，而应该看它能不能在历史语义中保持一致性。

七、语义层需要持续更新
还有一个很容易被忽略的问题：语义不是一次性建设出来的。
业务会变，表会变，指标会变，用户问法也会变。
所以 AI 取数系统不能只做一个静态知识库，而要有更新闭环。
我会把更新来源分成三类。
第一类，系统元数据更新 Ossie。
当 Hive、StarRocks、PostgreSQL 里的表结构发生变化，或者指标平台里的定义发生变化，应该同步更新 Ossie 模型。
新增字段、字段类型变化、表下线、指标口径变更，都需要进入版本管理和校验流程。
第二类，历史问句沉淀业务知识。
用户每一次追问、纠错、确认，都是很有价值的语义信号。
比如用户说：
「这里的新用户不是注册新用户，是首次支付用户。」
这句话就不应该只停留在一次对话里。
它应该被沉淀成业务知识，关联到对应指标、字段、历史问句和校验规则。
第三类，用测试集评价效果。
AI 取数系统一定要有测试集。
测试集里应该包含高频问题、复杂 join 问题、易混淆指标问题、特殊业务规则问题、枚举值映射问题和历史口径问题。
每次语义模型、提示词、检索策略或 SQL 生成逻辑变化之后，都要跑一遍测试集。
否则你很难知道系统是变好了，还是只是这次回答看起来更顺。
这套闭环跑起来之后，AI 取数系统才会从「一次性问答工具」变成「持续学习业务语义的系统」。
八、Ossie 在这里的真实价值
如果只用一句话总结，Ossie 的价值不是让 AI 更会写 SQL，而是让 AI 更少误解业务。
它把数据集、字段、关系、指标和 AI 上下文变成一份机器可读的语义契约。
它让 Hive、StarRocks、PostgreSQL 这些底层系统可以在语义层被统一描述。
它让事实表、指标表、派生指标、衍生指标之间的关系更清楚。
它也让语义定义有机会进入 Git、校验、评审、转换和自动化流程。
但它不替代 Wiki。
不替代图 + 向量库。
不替代指标治理。
也不替代数据建模。
更现实的做法，是把它放在 AI 取数链路的中间：
上游接数仓元数据、指标平台、数据标准和业务文档。
中间用 Ossie 形成结构化语义模型。
旁边用 Wiki 补业务解释，用图 + 向量库补关系推理。
下游服务 Text-to-SQL、数据分析 Agent、BI、可视化和自动报表。
当用户问一个业务问题时，系统不再只是把问题丢给模型。
它会先找到可用语义，再选择查询路径，再生成 SQL，再验证逻辑，再执行取数，最后解释结果。
这才是我理解的 Ossie 实战。
不是把一个开放标准摆进架构图里。
而是让它成为 AI 取数系统里的语义地基。
