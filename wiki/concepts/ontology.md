# 本体论 (Ontology)

## 一句话定义

本体论（Ontology）是知识工程中用于形式化描述某一领域内概念及其关系的框架。与语义层（Semantic Layer）不同，本体论侧重概念的哲学定义和形式逻辑，语义层侧重业务指标的映射和查询。

## 核心原理

本体论在 AI 时代重新变得重要，因为它解决了"AI 如何理解世界"的基础问题：
- 定义领域内的实体（类）及其属性
- 定义实体间的关系（对象属性和数据属性）
- 定义推理规则（公理和约束）

## 本体论 vs 语义层

| 维度 | 本体论 (Ontology) | 语义层 (Semantic Layer) |
|------|-------------------|------------------------|
| 关注点 | 概念定义和逻辑关系 | 业务指标和数据映射 |
| 表示语言 | OWL, RDF | SQL, YAML, 元数据配置 |
| 代表工具 | Protégé | Palantir Foundry |
| 经典教材 | Pizza Ontology (斯坦福) | — |

## 在 AI Agent 中的应用

- **知识图谱构建**：本体论为 Agent 提供领域概念的结构化定义
- **Schema Linking**：AutoLink 等工具将数据库结构映射到本体概念
- **语义搜索**：基于本体的查询扩展和推理

## 企业级 AI Agent 中的 Ontology（2026 年实践视角）

### 本质：给 AI 一张企业业务地图

Ontology 不是方法论文档，也不是单独工具。它是**一套让 AI Agent 看懂企业业务、并按企业规则办事的建模方法**，落地后表现为企业语义层/业务对象层，最终被包装成平台或工具。

**核心思路**：不要直接让 AI 面对一堆零散系统，先给它一套能理解企业业务的结构。大模型是 Agent 的大脑，工具是手脚，Ontology 是 Agent 对企业业务的理解方式。

### 四步建模法

**1. 定义对象（Object）**
企业所有重要对象都要被语义统一。同一个词在不同系统可能含义不同（销售系统里的"客户"是公司，财务系统里是开票主体，客服系统里是联系人）。

**2. 定义关系（Relations）**
对象之间怎么关联：订单属于哪个客户？客户对应哪些合同？仓库服务哪些区域？

**3. 定义动作（Actions）**
对象可以做什么：修改工单状态、生成采购申请、发起退款、调整排产。AI 不是随便点按钮，要知道能不能做、谁能做、什么条件下能做。

**4. 定义规则（Rules）**
什么能自动做，什么只能建议，什么必须审批。

### 和 RAG 的区别

| 维度 | RAG | Ontology |
|------|-----|----------|
| 解决问题 | AI 去哪里找信息 | AI 怎么理解企业并在企业里做事 |
| 信息来源 | 企业文档/资料 | 业务对象、关系、动作、规则 |
| 输出 | 回答/摘要 | 可执行的操作路径 |
| 典型场景 | "这个合同有没有违约条款" | "这笔退款能不能自动处理，处理完写回哪个系统" |

RAG 解决"知道什么"，Ontology 解决"怎么运转"。

### 典型业务用例

**制造业排产**：收到加急订单 → 查客户等级/原料库存/产线负载 → 评估插单影响 → 生成多方案 → 推送给对应负责人确认 → 写回排产系统。

**医院床位管理**：查可用床位 → 匹配患者病情/科室要求 → 检查护理资源 → 生成调配建议 → 交给值班医生确认。

**客服退款**：查客户/金额/退款期限/发货状态/风险等级 → 判断是否自动退款 → 自动处理并同步 OMS 和财务系统，或提交人工审批。

### 与同类方案对比

本体层（Ontology Layer）不是银弹——它在"接口准确性"和"行为可控性"两个维度上是最直接可落地的解法，与 MCP、RAG、Fine-tuning 互补而非替代。

| 方案 | 核心机制 | 接口准确性 | 权限/审计 | 更新成本 |
|------|---------|-----------|----------|---------|
| 本体层 | 结构化元数据约束调用行为 | ★★★ 精确 | 原生支持 | 小时级重生成 |
| MCP | 标准协议连接外部工具 | ★★☆ 依赖实现 | 需额外设计 | 更新 Server |
| RAG | 检索文档扩充上下文 | ★☆☆ 难精确 | 几乎不支持 | 重新入库索引 |
| Fine-tuning | 训练阶段烧入业务知识 | ★★☆ 领域适应 | 不支持 | 天至周级重训 |

### 落地参考

- **工程治理**：命名是一切基础。表名用中文语义（`库存补货单`而非 `GLC_JJPCHZB`），ID 明确所属实体，枚举值加备注，服务端命令用谓宾结构。
- **工具生态**：huozige-ontology-builder（扫描活字格工程生成本体）、huozige-web-app-cli（Agent 调用业务 App）、MQTT 通道（OpenClaw 接口适配）。
- **交付质量**：LLM as a Judge 自动化测试——收集标准用例 + 执行记录 + 调用日志 + 本体文件，由评判模型自动打分。
- **网络架构**：Ontology 放在 DMZ，业务系统在内网不直接暴露，通过 MQTT 通讯，用户身份全程透传复用现有 ACL。
