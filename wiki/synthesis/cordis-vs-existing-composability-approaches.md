# Cordis 与既有组合方案逐项对比

> 对照物：论文《A Programming Paradigm for Spatiotemporal Composability》实现的 Cordis 元框架，与 **React useEffect / Spring DI / Erlang 热升级 / DSU（动态软件更新）** 四类"既有方案"。目的是回答同一句话：**当组件在运行中装载、卸载、替换时，谁负责把副作用收干净、谁负责把依赖接回来。**
> 参考页：[[时空可组合性编程范式 — Cordis 与动态组合演算]]

## 概述

这四类方案并非都"解决同一个问题"，把它们放在一起才有意义——它们各自只覆盖"时空可组合性"两轴中的一部分，且粒度、责任边界差异很大：

- **React useEffect**：UI 渲染层的副作用生命周期，靠开发者手写 cleanup，只在组件粒度、且没有依赖图。
- **Spring DI**：对象组合 + 依赖注入，依赖拓扑在启动期解析，生命周期绑定容器，运行时依赖变化基本不响应。
- **Erlang 热升级**：模块级真正的运行时热替换 + 进程状态迁移（`code_change/3`），时间维度接近 Cordis，但副作用撤销与依赖协调靠手写脚本。
- **DSU**：运行中替换程序/函数并迁移状态，是"重启动态更新"的学术路线，迁移函数手写，几乎不管依赖。

Cordis 的主张是：把 effect（副作用）与 coeffect（依赖）都做成**运行时一等对象**，只用一套 Context 同时覆盖"时间可组合性（离场可撤回）"和"空间可组合性（入场可重连）"。

## 对比坐标系

| 维度 | 问题 |
|------|------|
| 组合粒度 | 组合单元是函数、组件、Bean、模块还是进程/容器 |
| 时间可组合性 | 组件离开后，能否完整、安全地撤回它对共享环境做过的修改 |
| 逆操作责任方 | 撤销动作由谁编写 |
| 撤销顺序 | 多步副作用回滚时，顺序是否有语义保证 |
| 空间可组合性 | 依赖能否声明、发现、解析 |
| 依赖解析时机 | 启动时一次性 / 运行时持续 |
| 依赖变化的响应式 | provider 更换时消费者能否被自动通知并重连 |
| 生命周期次序保证 | 是否有"提供者先存活、后退出"这类结构性保证 |
| 热替换机制 | 运行中替换实现的手段 |
| 运行中状态保持 | 替换时进程/组件状态是否保留 |
| 失败与回滚语义 | 加载/替换失败时系统是否保持一致 |
| 逆操作是否被校验 | 运行时是否验证"逆真的能逆转" |
| 作用域与系统边界 | 可逆的边界落在哪 |
| 典型代价 | 换来的能力要付什么 |

## 逐项对比

### React useEffect

- **粒度**：函数组件（渲染周期）。组合边界是组件树。
- **时间可组合性**：`useEffect(() => { ...; return cleanup }, deps)` 提供了 cleanup 回调，在依赖变化或组件卸载时执行。但清理**仅覆盖该 effect 自身**，跨注册（第三方库里再注册的监听）无归属跟踪；`deps` 靠手写，漏写/多写都会出错。
- **逆操作责任方**：开发者手写 cleanup 闭包。
- **撤销顺序**：cleanup 按 Hook 声明顺序执行，属于"组件内约定"，不是全局 LIFO 语义保证。
- **空间可组合性**：props / React Context 传值，没有类型化依赖图，没有 `inject` 声明。
- **依赖解析时机**：渲染时直接读取；无运行时注册表。
- **依赖变化响应**：`deps` 变化 → effect 重跑（cleanup → setup）；Context 变化 → 重渲染。**响应靠手写依赖数组**。
- **生命周期次序**：无 provider/consumer 生命周期语义——Context Provider 卸载不会等待消费者清理完。
- **热替换**：Fast Refresh / HMR（主要面向开发期）；状态保留"尽力而为"，非结构保证。
- **状态保持**：尝试保留局部 state，但副作用清理无结构保证。
- **失败语义**：渲染错误靠 Error Boundary 兜；无事务回滚。
- **校验逆**：无。
- **边界**：面向 UI 副作用，不是通用运行时组合模型。
- **代价**：心智负担（deps、闭包陷阱），但生态成熟、开销低。

### Spring DI

- **粒度**：Bean（对象/组件），容器负责装配。
- **时间可组合性**：`@PreDestroy` / `DisposableBean` / `destroy-method`，容器关闭时调用。**不跟踪副作用**，无法细粒度卸载单个 Bean 并回滚其外部影响。
- **逆操作责任方**：开发者写 destroy 方法；容器只负责在合适时调用。
- **撤销顺序**：容器按**依赖逆序**销毁依赖方（拓扑保证）——这点比 React 强。
- **空间可组合性**：构造/字段注入，`@Autowired` / `@Qualifier`，靠接口解耦，依赖声明是"静态拓扑"。
- **依赖解析时机**：启动时（`@Lazy` 可延迟），一次性解析。
- **依赖变化响应**：基本没有；`@RefreshScope` / Spring Cloud Context 只能刷新配置属性，不是组件级响应式重连。
- **生命周期次序**：DI 图有依赖顺序，但运行时更换 provider 不会自动触发消费者重连。
- **热替换**：DevTools 重启（classloader 级），不是真热替换；不能卸载单个 Bean。
- **状态保持**：重启即丢。
- **失败语义**：无回滚。
- **校验逆**：无。
- **边界**：进程/应用级生命周期。
- **代价**：启动慢、上下文重；工具链成熟。

### Erlang 热升级

- **粒度**：模块 / 进程（`gen_server` 等），天然进程隔离、不共享内存。
- **时间可组合性**：代码可热替换，进程通过 `code_change/3` 迁移状态。但**副作用（消息、ETS、注册名、DETS）没有自动逆操作**。
- **逆操作责任方**：开发者写 `code_change/3` + `.appup` 升级脚本。
- **撤销顺序**：`.appup` 指令（`suspend`/`resume`/`load_module`）显式控制；supervisor 树提供拓扑。
- **空间可组合性**：OTP 应用依赖（静态）；运行时依赖靠进程注册表（`whereis`）+ 监督树。
- **依赖解析时机**：启动时解析应用依赖；进程注册在运行时。
- **依赖变化响应**：supervisor 重启策略（`one_for_one` 等）自动拉起崩溃进程；但**依赖服务升级需要手动编排**。
- **生命周期次序**：supervisor 树提供父子次序 + 进程链接。
- **热替换**：**真正的模块级运行时热替换**（不重启 VM，进程状态可保留）——这是 Cordis"时间可组合性"最强的近亲。
- **状态保持**：保留（靠 `code_change` 迁移），但不自动回滚。
- **失败语义**：`release_handler` 有升级/回滚机制，但复杂；失败可能留下不一致。
- **校验逆**：无（`code_change` 正确性全靠开发者）。
- **边界**：单 VM 内；向外发射的消息同样不可逆。
- **代价**：升级脚本复杂、心智负担高；但容错/热更仍是业界标杆。

### DSU（动态软件更新）

- **粒度**：程序 / 函数（OPUS、Kitsune、JVMTI 等为代表）。
- **时间可组合性**：运行中替换代码并迁移状态；**逆操作（回滚到旧版本）通常不提供**。
- **逆操作责任方**：开发者手写 state migration function。
- **撤销顺序**：无标准（各工具自定义）。
- **空间可组合性**：一般**不提供**依赖管理，只做代码替换。
- **依赖解析时机**：N/A。
- **依赖变化响应**：无。
- **生命周期次序**：无。
- **热替换**：核心能力，但**每个工具一套**，不成标准。
- **状态保持**：靠手写 migration。
- **失败语义**：视实现，常缺乏事务回滚。
- **校验逆**：无。
- **边界**：VM / 语言层。
- **代价**：迁移函数成本高、与实现强耦合。

### Cordis（对照基准）

- **粒度**：组件/插件（每次挂载一个 fiber 实例）。
- **时间可组合性**：**revertible effects**——每个原子操作在"执行位置"绑定并上交逆函数，运行时自动复合（twisted monoid，逆序累积）、LIFO 回滚。开发者**无需编写整段 unload 路径**。
- **逆操作责任方**：开发者只给"每个原子操作的逆"（比 DSU 的整段 migration 更细、更结构化）。
- **撤销顺序**：严格 LIFO（代数内建）+ 跨组件拓扑次序。
- **空间可组合性**：**reactive coeffects**——`inject` 声明依赖集，类型化依赖上下文，满足度 `σ ⊨ d` 可判定。
- **依赖解析时机**：**运行时持续解析**（每次 Context 变化重算）。
- **依赖变化响应**：三态通知 `activating / deactivating / neutral`，自动激活/停用组件；provider 更换自然分解为"失活 → 激活"。
- **生命周期次序**：**提供者生命周期严包含消费者**（提供者先存活、后退出；消费者先退出、后存活）。
- **热替换**：HMR + **事务性重载**（旧 fiber `dispose → recover` → 新 fiber 实例化，任一步失败整体回滚，不进入半重载态）。
- **状态保持**：组件级；业务事实靠 session event log 另行保存。
- **失败语义**：加载中途失败自动回滚；单个 dispose 失败不级联；Context 始终保持一致（Preservation）。
- **校验逆**：**不校验**——逆能逆转、操作能交换，是组件作者的义务（论文以 witness 形式要求，运行时不验证）。
- **边界**：系统边界内可逆；跨边界的 emission（邮件、网络包、扣款）只能补偿。
- **代价**：必须为原子操作提供逆；时间轴依赖闭包 + 运行时模块加载，空间轴依赖类型级依赖声明 + Proxy 拦截。

## 横向汇总

| 维度 | React useEffect | Spring DI | Erlang 热升级 | DSU | Cordis |
|------|-----------------|-----------|---------------|-----|--------|
| 粒度 | 组件 | Bean | 模块/进程 | 程序/函数 | 组件/fiber |
| 时间可组合性 | 局部 cleanup | 销毁钩子 | 状态迁移 | 代码替换 | **自动可逆 effect** |
| 逆操作谁写 | 开发者 | 开发者 | 开发者 | 开发者 | 开发者（仅原子步） |
| 撤销顺序 | Hook 顺序 | 依赖逆序 | appup 脚本 | 无标准 | **严格 LIFO + 拓扑** |
| 空间可组合性 | 弱（Context） | 静态 DI | 弱（注册表） | 无 | **响应式 coeffect** |
| 依赖解析 | 渲染时 | 启动时 | 启动时 | — | **运行时持续** |
| 依赖变化响应 | 手写 deps | 基本无 | 手动编排 | 无 | **三态自动** |
| provider/consumer 次序 | 无 | 部分 | supervisor 树 | 无 | **结构性保证** |
| 热替换 | Fast Refresh | DevTools 重启 | **真模块热更** | **真代码替换** | **HMR + 事务重载** |
| 运行状态保持 | 尽力而为 | 丢 | 保留 | 靠手写迁移 | 组件级 + event log |
| 失败回滚 | 无 | 无 | 复杂 | 视实现 | **事务回滚** |
| 校验逆 | 无 | 无 | 无 | 无 | 无 |
| 边界 | UI 副作用 | 应用级 | VM 内 | VM/语言层 | 系统边界内 |

## 关键结论

1. **两轴同时覆盖的只有 Cordis。** Erlang 与 DSU 在"时间轴"（热替换 + 状态保留）很强，但空间轴（依赖声明/响应式重连）很弱；Spring 相反，空间轴（静态 DI）强、时间轴弱；React 两轴都弱，且只限 UI。
2. **"手写逆/迁移"是所有方案的共同成本，区别在粒度。** DSU 要求手写整段状态迁移函数，React/Spring/Erlang 要求手写卸载回调或 `code_change`；Cordis 把它下推到"单个原子操作"，由运行时自动复合——这是结构性差异，不是量级差异。
3. **顺序保证是分水岭。** Spring 有依赖逆序销毁、Erlang 有 supervisor 树，但它们管的是"静态拓扑"；只有 Cordis 同时给出**严格 LIFO 撤销**和**提供者严包含消费者**的运行时次序语义。
4. **响应式重连是 Cordis 独有的。** 其余方案在 provider 更换时都要人工干预（重启、刷新、手动编排），Cordis 把它变成 Context 变化的自动后果。
5. **没有免费的午餐。** Cordis 的代价是：必须为原子操作提供逆、依赖特定运行时能力（闭包/生成器/Proxy）、且**运行时不校验你的逆写对了**；跨系统边界的副作用仍只能补偿。Erlang/Spring 则用"更粗粒度但更省心"的方式回避了这些问题。
