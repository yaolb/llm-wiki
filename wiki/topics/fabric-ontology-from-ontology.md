# 从本体论到 Fabric Ontology

> 素材：微信公众号「Deon的学习小站」《从本体论到 Fabric Ontology》（2026-09-15），原文归档于 `raw/fabric-ontology-from-ontology.md`（约 4.3 万字 + 19 张图）。
> **来源性质：长篇教学/实操笔记**，作者自带「证据边界」声明（见文末）——这是本篇最可贵的地方：**明确区分了官方文档陈述、界面实拍、实测发现与推演**。

## 一句话

一篇把「本体」从**哲学 → 语义网 → 大模型时代 → 微软 Fabric 产品落地 → 选型**一次讲通的超长文，用**「连锁奶茶店冷链断裂追责」**一个案例贯穿到底（一批奶茶变质，要查"哪个环节坏的、还影响哪些批次、该通知哪些门店"）。

## 结构（三篇 + 四附录）

### 第一篇 · 本体是什么（1–4 章）

- **1 一个 SQL 回答不好的问题**：七类对象串起来的追问。SQL 要写三段 join 才能答，**代价在于"连接路径只存在于人脑里"**
- **2 从哲学到计算机**：本体论（ontology，研究"存在什么"）→ 计算机借走的是什么；**考据了被误传的 Gruber 定义**；`术语表 → 分类学 → 本体` 逐级加了什么；**本体 vs 数据库 schema 的根本差别**（表达含义 vs 描述存储）
- **3 语义网、知识图谱留下了什么**：RDF（三元组）→ RDFS（可推理）→ OWL（更强表达力、更贵）→ SPARQL；**为什么语义网没按原计划普及**（败在 "shared" 上——需权威、边界清晰、激励一致）；知识图谱的实用主义转向
  - **关键分叉：RDF 图 vs 属性图**——RDF 边不能直接带属性（要 reification 造节点），属性图可以；工业界大体选了**属性图 + GQL**（2024 年 GQL 成为 **ISO/IEC 39075**，SQL 之后第二个数据库查询语言标准）
- **4 为什么大模型让本体重新变重要**：
  - **LLM 面对企业数据的三种失败**：**术语歧义**（`batch_store_id` vs `complaint_store_id`，字段名相似语义相反）、**关系臆测**（猜 join 路径，错了也不说）、**无法解释**（说不出业务推理链）
  - 共同根源：**模型拿到的是表结构，不是业务含义**
  - **grounding**：给表结构有用但上限明确——缺的正是"字段业务含义 / 关系 / 关系叫什么 / 类型层级 / 基数约束 / 同义词"
  - **从回答问题到执行动作**：agent 要知道「有哪些动作 / 前提条件 / 执行后果」——这正是 Palantir 把本体定义为「组织的数字孪生」（语义元素 + 动力学元素）的原因

### 第二篇 · Fabric 怎样实现这些能力（5–9 章）

- **5 Fabric IQ 的定位**：属于微软 **Microsoft IQ** 四块之一（Work IQ / Foundry IQ / Web IQ / **Fabric IQ**）。Fabric IQ 自身**三层**：
  `运营智能层（Ontology）← 业务概念/关系/规则/动作` / `商业智能层（Power BI 语义模型）← 指标口径` / `统一数据层（OneLake）← 数据本身`
  - 六类 Item：本体 / Power BI 语义模型 / **图 Graph** / 计划 Planning / 数据代理 / 操作代理
  - 官方金句：**"Ontology declares what connects and why. Graph stores and traverses those connections."**
  - **实测发现**：建一个本体，工作区里会**自动冒出三个 Item**（`Lakehouse` + `SQLEndpoint` + `GraphModel`）——本体不是独立存储，是**一层声明**
  - **技术路线：属性图 + GQL，不是 RDF + SPARQL**；类型/实例严格区分（不允许 RDFS 那种"类同时是实例"）→ **为"一个组织内部"设计，不为跨组织开放协作设计**
- **6 对象模型**：实体类型（≠表，可绑多张表）/ **实体类型键**（硬性要求，且键类型只能是 string 或 integer）/ 属性（**静态 vs 时序**，静态绑定**每个实体类型只能一个**）/ 关系（**有名字、有方向**，可带属性与基数规则）/ 实例与本体图
  - **属性名是全局命名空间**：1–26 字符、全局唯一 → 不能 `Store.name` 和 `Truck.name` 并存，必须 `store_name` / `truck_name`（RDF 用 IRI 解决同名，Fabric 用"你自己起不同的名"）
  - ⚠️ **上游数据更新需手动刷新才可见**——本体图是**物化的，不是视图**
- **7 数据绑定**：绑定**不复制源数据**（对比 ETL / 视图 / 本体绑定三者的「数据在哪 + 变更传播」）；**必须先做静态绑定**再做时序；类型映射表（复杂类型 array/map/struct 一律变 string，嵌套 JSON 要先 ETL 展平）
  - **限制清单（做方案前必看）**：源表必须是**托管表**（外部表/快捷方式不行）、**不能启用 OneLake 安全**、**不能启用列映射**（⚠️ 列名含**空格**会**自动**启用列映射 → 表就绑不上，且原因完全不显眼）
  - **实体类型键是静默的拦路虎**：没定义键 → **Save 不生效且无报错弹窗**，页面看起来保存成功，退出再进才发现属性是空的
- **8 查询**：本体的路由作用——**遍历部分交给 Graph（GQL）、时序部分交给 Eventhouse（KQL）**，本体层本身不是执行引擎而是**路由器**；**NL2Ontology**（自然语言→结构化查询，保证过滤/连接/单位/有效期与本体定义一致）；给 Data agent / Operations agent 用；再次强调**手动刷新**是方案硬约束（本体不适合秒级实时，那是事件流 + Activator 的活）
- **9 动手建冷链本体**：租户设置是第一道门（不开的话「新建项」里**根本看不到本体选项**）；四张表 + 三条关系（`deliveredBy` / `deliveredTo` / `locatedIn`）；**8 条踩坑清单**（导览浮层挡住按钮、点表名≠点圆圈、键未定义静默失败、列名空格、属性重名、外部表、新行看不到）

### 第三篇 · 选型（10 章）

统一命题 + 8 条比较轴（本体层从哪来 / 图存储遍历 / 数据要不要搬 / 推理能力 / 动作与写回 / AI 集成 / 跨组织协作 / 上手门槛）。四个候选：

- **vs Palantir Foundry Ontology**（最直接对标）：Palantir 把「**动力学元素**」设计进本体本身（action types / functions / interfaces 类型多态），Fabric 当前预览期重心在语义与 grounding，动作要靠 **Activator + 操作代理 + UDF 拼**。Fabric 的反向优势：本体与 Power BI 语义模型**同平台同三层结构**
- **vs RDF/OWL 标准栈**：Fabric 给不了强逻辑推理与跨组织 IRI 合并；**领域已有成熟标准本体（SNOMED CT / FIBO / Gene Ontology）优先复用**
- **vs Neo4j**：同是属性图，差别在**本体层在哪**——Neo4j 的 "schema" 仅指**索引和约束**（schema optional），未提供承载概念/同义词/约束语义的一等结构，本体层要自建；差别在**数据引力**（Neo4j 要导数据，Fabric 直接绑 OneLake 但需手动刷新）与**schema 哲学相反**（先放数据 vs 强制先定义）
- **基线：直接给 LLM 喂表结构**（真正的比较基准）：
  | 情况 | 够用吗 |
  | --- | --- |
  | 表少（十几张内）、命名规范、有外键 | ✅ |
  | 问题集中在单表或两表 join | ✅ |
  | 一次性分析不需复用 | ✅ |
  | 表多、命名混乱、无外键 | ❌ 模型会猜错 |
  | 需要三跳以上遍历 | ❌ 容易错且难验证 |
  | 同名字段语义不同 | ❌ 典型翻车点 |
  | 需要解释推理链给业务方 | ❌ 做不到 |
  | 多团队/工具共享同一套定义 | ❌ 提示词不是共享资产 |

**10.7「什么时候不该用本体」可能是全篇最重要的一节**——成本在四处（定义 / 绑定 / 维护 / 刷新），三类不适合：① 单表或两表的问题 ② 数据质量还没解决（关键外键填充率 <90% 先去修数据）③ 组织还没准备好达成一致（两周内签不下前五个核心概念就别上）。
**该用的信号**：三跳以上遍历且路径常变 / 同概念多系统表示反复造成误解 / 要给 AI agent 用且要求答案可解释 / 多团队共享定义 / 有能力也有意愿维护。
作者对贯穿案例的**诚实结论**：奶茶店这个规模，「本体是划算但不是必需的」，讲课很好，**用它论证客户必须买本体则是夸大**。
