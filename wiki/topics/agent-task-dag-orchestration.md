# 任务 DAG 多 Agent 编排：Anthropic 费马大定理项目的启示

> 素材分析：微信公众号「司徒驴三」《Anthropic 提出一种新的多 Agent 编排方式》（2026-09），原文归档于 `raw/anthropic-multi-agent-dag-orchestration-wechat.md`。文章是对 Anthropic 2026-09-04 公开的 Lean 4 多 Agent 实验（Prove2Me 平台）的方法论提炼。

## 概述

一句话立场：**Agent 可以离开、可以换人，任务状态必须留在系统里。**

Anthropic 用几十个 Claude Agent 在 Lean 4 中协作，11 天生成约 **1300 万行** Lean 代码、证明 **30,300** 个中间定理（29,500 个进入最终证明），完成费马大定理的端到端机器验证。真正的教训不在"如何启动几十个 Agent"，而在**协作失效的根因**：Agent 能完成局部证明，合到一起却丢失项目进度、协作随之失效。修复办法是接入 Prove2Me，用**定理依赖图（DAG）**组织工作——把"任务状态"从"主 Agent 的对话记忆"中剥离出来。

## 1. 任务契约（Task Contract）：节点存的是结果，不是角色

| 要素 | 含义 | 反面 |
|------|------|------|
| **节点** | 一份形式化声明（条件 + 结论），即"要交付的结果" | "负责分析""负责写代码"——只描述分工，不定义完成 |
| **边** | "依赖其结果"这一事实 | A 排在 B 前面 ≠ B 依赖 A（会把并行排成串行） |
| **无环** | 不能用 A 证 B 再用 B 证 A | 把一圈未成立的结论当成证明 |

- **声明与证明分离**：声明固定后可有多个证明；某个证明失败不必换掉目标。
- **对软件的类比**：节点写成"切换账号后旧请求不能更新新会话数据"（行为约束），而不是"检查登录模块"（实现动作）。前者给约束、留实现空间（取消请求 / 校验会话版本 / 改缓存写入点），共享同一组验收。

## 2. 证明草图（Proof Sketch）：子任务未完成，父任务也能推进

- **草图是可被检查的代码**，不是"接下来该怎么做"的计划；它可引用尚未证明的子定理，先建立**有条件推导**。
- 平台状态 `SKETCH_ACCEPTED` = 推导通过检查、但引用了未完成的定理；子定理全部证明后父目标才转 `Proved`。
- 由此得到一条可迁移的工程原则：**"方案成立"与"工作完成"是两个状态。**
- **多候选路线**：T 可经 A+B 达成，也可经 D 达成——依赖必须归属到各方案，不能混成"必须全做完"的清单。
- **分解本身是产物**：编排者要说明子任务完成后如何支撑父目标。

## 3. 调度：Agent 从哪里找到下一项工作

- 入口顺序：**里程碑定位方向 → 未解决的叶子节点（可继续展开的工作）→ 先读已有分解、失败尝试、讨论记录**。
- **反模式**：只让 Agent 在整张图里挑任务 → 完成数猛涨但主目标不动（人人都去做容易且与当前阻塞无关的节点）。需要知道"哪条修复路线在等这个结果"，再由优先级策略分配资源。
- **复用要进流程**：领取任务之后、生成方案之前，先搜已有产物。**自然语言用于找候选，正式条件决定是否适用**（"单线程不会重复写入"不能直接搬到并发场景）。
- **失败记录可查**：哪条路试过、基于哪个版本、为何放弃——让 Agent 重启后能恢复调查。

## 4. 状态与验证：完成状态必须有依据

- **同名任务、条件不同**的隐患：一方改目标、另一方按旧条件干，各自通过检查也可能接不上。Prove2Me 允许改说明/来源/标签，**不开放形式化声明的修改**——需求变更 = 发新条目，让引用者知道自己依赖的是哪一个声明。
- **仓库分离**：`Theorems/` 声明、`P2M/Sol/` 证明、`Definitions/` 定义；依赖靠 import 追踪。
- **验证器不可省**：Agent 写"完成"只是**一次报告**，系统要检查产物是否满足目标，下游才能使用。数学侧有 Lean 证明检查、Comparator 核对目标/定义、独立内核 nanoda 三层。
- **软件没有等价物**：测试通过 ≠ 全部输入下正确；Agent 为过检删断言时，绿色报告反而掩盖退步 → **验收条件与检查程序必须独立管理，改动要留理由和审核**。
- **边界声明**：公开的只是机制，**不等于 Anthropic 内部 harness 的完整实现**（别把自补的锁/队列/重试写成对方已公开的设计）。

## 5. 落到自己的 Agent 系统

以"退出登录后旧请求污染新账号数据"为例的编排流程：

1. **从一个能复现的问题开始**，而不是先定几个 Agent 角色；
2. 先写**验收场景**（旧请求在途 + 用户切换账号 → 旧响应不得改变新会话界面与缓存）；
3. 拆出**两条并行调查**：构造时序复现污染 / 追踪网络层到缓存、界面的写入路径；交付物是复现代码、调用位置、日志，而非"问题可能在缓存"的总结；
4. 修复方案允许**带未确认前提**（如同一份带条件的草图），前提由调查结果回填，最终在目标代码版本上跑验收。

跨会话需要持久化的任务字段（示例，非 Prove2Me 数据结构）：

| 保存什么 | 解决什么问题 |
|---|---|
| 目标与验收条件 | 接手者知道要交付什么 |
| 所属方案与依赖 ID | 哪个方案在等哪些结果 |
| 输入版本、产物地址 | 代码改动后追溯结果是否过期 |
| 验证记录 | 区分提交 / 通过检查 / 最终验收 |
| 失败原因、后续线索 | 换人后能继续调查 |

Worker 循环：读目标 → 查已有结果 → 领取任务 → 提交产物或分解方案 → 等验证 → 选下一项。**主 Agent 保留规划与审查，但不当每次交接的中转站。**

工程补丁（DAG 本身不提供）：领取需**原子操作** + 租约期限（中断可回收、旧 Worker 不能覆盖新提交）；**验证结果绑定输入版本/内容哈希**，上游变更后重查受影响分支；拆不出清晰契约的改动**放进同一集成任务**，不为画 DAG 硬拆。

**验证扩展性的最小实验**：2 个 Worker + 1 个有依赖的修复目标，运行中打断一个 Worker 换人接手，看能否找回输入、理解未完成前提、交出可验收结果。

**适用边界**：只是"几个 Agent 各写一份独立评审给人看" → 主 Agent 分发汇总就够了；**需要跨会话、复用中间产物、多人接力** → 才值得把任务状态存进系统。
