# Apache Ossie 实战：给 AI 取数系统搭一层业务语义地基

> 素材分析：微信公众号「胡二说八道」《Apache Ossie 实战：我如何给 AI 取数系统搭一层业务语义地基》（2026-08-22），原文归档于 `raw/apache-ossie-in-practice-ai-data-retrieval-wechat.md`。
> 关联：本篇是 [[从 Arrow 到 Iceberg 到 Polaris 到 Ossie：语义标准化的最后一块拼图]] 的**续篇**——前篇讲"为什么需要开放语义标准"，本篇讲"**怎么用**"。

## 概述

作者从自己做 AI 取数、AI 报表系统的经验出发，给出一个核心判断：

> **真正难的不是让大模型写 SQL，而是让它知道这家公司里的数据到底是什么意思。**

一条完整的 AI 取数链路：

```
用户问题 → 找表 → 生成 SQL → 取数 → 代码二次处理 → 可视化
```

真正卡住的地方在**前两步**：从上万张表里找对表、按正确业务口径生成 SQL。而且这里的"准确"不只是语法正确——还要知道**事实表 vs 指标表怎么选**、**指标之间的依赖关系**、**哪些字段不能直接加总**、**某些业务线的特殊过滤逻辑**、**用户黑话映射到哪个内部字段**。

这些语义若只散落在 Wiki、字段注释、历史 SQL、分析师经验、BI 配置里，AI 就最容易写出**最危险的 SQL**：

> 看起来很合理，跑起来也有结果，但**业务口径是错的**。

因此作者主张把业务语义知识库拆成**三层**：

| 层 | 承担 | 内容形态 |
|----|------|----------|
| **Ossie** | 结构化语义 | 可执行、可交换的语义模型（JSON/YAML） |
| **Wiki** | 业务解释与例外说明 | 背景、争议、演进、自然语言解释 |
| **图 + 向量库** | 对象关系与反向映射 | 关系推理、多路召回 |

## 1. 先别急着让模型写 SQL

第一版 AI 取数系统往往从 Text-to-SQL 开始。Demo 场景容易跑通（几十张表、字段名干净、口径简单），但真实企业环境不同：

- 有 Hive、StarRocks、PostgreSQL 等多套数据库；
- 同一业务对象在不同系统里有多张表；
- 历史遗留字段名非常抽象；
- 明细事实表 / 宽表 / 指标汇总表混杂；
- 有些字段"看起来像金额"，实际只是中间计算字段。

**以"收入"为例的失败模式**：模型可能去事实表 `sum` 支付金额、也可能去指标表取已加工好的收入指标、还可能把 **GMV / 实收金额 / 净收入 / 确认收入**混在一起。

因此模型必须知道**指标层级**：事实表原始字段 → 原子指标 → 派生业务指标 → 衍生指标。这正是 Ossie 发挥作用的地方——**它不是替模型写 SQL，而是先把"什么是数据集/字段/指标、它们之间怎么关联"变成机器可读的语义模型。**

## 2. Ossie 的第一件事：让表和指标不再混乱

Apache Ossie 的定位是**开放的语义模型交换标准**（vendor-agnostic semantic model specification，面向 analytics / AI / BI 生态），用 JSON / YAML 描述语义模型，减少工具间语义元数据不一致。AI 取数场景中最相关的对象：

- **Dataset**：业务数据集（对应事实表、维表、宽表或逻辑查询）
- **Field**：字段（类型、表达式、是否时间维度等）
- **Relationship**：数据集间关联（如订单表与用户表怎么 join）
- **Metric**：业务指标（支付金额、净收入、复购率、客单价）
- **AI Context**：给模型看的业务说明、同义词、使用指令、示例问题
- **Custom Extensions**：保留内部平台或厂商特有信息

**示例对比**：没有 Ossie 时，AI 面对"订单收入"只看到一堆表名（`dwd_order_detail` / `dws_order_summary_day` / `ads_revenue_dashboard` / `metric_finance_income_day`），字段注释不全时很难判断用哪张。引入 Ossie 后链路变得明确：

- 事实表：订单明细
- 原子指标：支付金额、退款金额、优惠金额
- 派生指标：净支付金额、有效订单数
- 衍生指标：客单价、复购率、收入贡献
- 可用维度：日期、地区、渠道、用户类型、商品类目
- 推荐数据集：高频分析场景优先用已治理的汇总表

**关键收益**：Ossie 可把 Hive / StarRocks / PostgreSQL 的语义统一到一套标准描述——底层存储、SQL 方言、物理表可以不同，但 AI 取数系统面对的是一套相对稳定的业务语义模型。

> 一句话点题：**AI 最怕的不是不知道，而是不知道自己不知道。** 结构明确后，模型至少能在边界内工作，遇到语义缺失也更容易暴露，而不是偷偷编一个答案。

## 3. 但 Ossie 不是全部——Wiki 仍然重要

有些内容**不适合全部塞进 Ossie**：业务领域怎么划分、某概念为什么这样定义、历史口径为什么调整过、特殊逻辑何时启用、数据标准背后的治理规则、内部用户 ID 命名与识别规则、跨部门用同一个词的语言习惯差异、历史问句沉淀的业务理解。这些有背景、有争议、有演进，更适合放 Wiki / 指标文档 / 数据标准文档。

**分工**：Ossie 负责"结构化、可执行、可交换"；Wiki 负责"解释、背景、例外、决策过程"。

**例子（有效用户数）**：Ossie 里定义 metric 表达式、数据集、时间字段、可用维度、同义词；而**为什么排除内部账号、内部账号识别规则、测试部门账号是否排除、2025 年前后规则差异**放 Wiki 更自然。

→ AI 生成 SQL 时：**先从 Ossie 拿结构化对象，再从 Wiki 拿业务解释与例外规则**。前者告诉它"应该查什么"，后者告诉它"为什么要这样查，以及哪些坑不能踩"。

## 4. 图 + 向量库补"关系"与"反向映射"

AI 取数中很多问题**本质是关系推理问题，不是文本检索问题**：用户说的词未必是字段名、说的值未必是库里的枚举值、问的指标未必落在一张表里。

**例**："帮我看一下小红书渠道最近一周的新客收入" 需要一串映射：小红书 → 哪个渠道枚举值 → 在哪些表的哪个字段 → "新客"用首购时间还是注册时间 → "收入"对应哪个指标 → 该指标能否按渠道和新老客同时拆分 → 推荐 join 路径。

图 + 向量库承载的关系：

```
字段值 → 字段 → 表 → 表 → 指标 → 指标
业务词 → 字段值
历史问句 → SQL 模板
报表 → 指标
```

**多路召回**：从 Ossie 找 dataset/field/metric/relationship；从 Wiki 找业务解释/特殊逻辑/数据标准；从图 + 向量库沿对象关系扩展候选表/字段/指标/枚举值；从历史问句库找相似问题与已验证 SQL → 合并排序 → 交给模型生成 SQL。

→ AI 取数从"让模型凭感觉写 SQL"变成"**让模型在语义约束下组装查询计划**"。

## 5. 更可靠的 AI 取数流程（八步）

1. **理解用户问题**：识别时间范围、业务对象、指标、维度、过滤条件、输出形式
2. **召回结构化语义**（Ossie）：dataset / field / metric / relationship，尤其指标依赖、时间字段、可用维度、SQL 方言
3. **召回业务知识**（Wiki）：概念定义、特殊口径、数据标准、内部规则、历史变更说明
4. **关系扩展**（图 + 向量库）：补齐字段值→字段、字段→表、表→指标、表→表的关系，处理用户语言与系统字段的反向映射
5. **生成 SQL**：基于候选语义对象生成，而非从全库表结构自由发挥
6. **执行取数**：按数据库类型选引擎（Hive / StarRocks / PostgreSQL）
7. **代码二次处理**：复杂排序、分桶、同比环比、异常点识别、图表数据整理
8. **可视化与解释**：输出图表/表格/自然语言解释，**保留 SQL、指标口径、数据来源以便追溯**

## 6. 验证比生成更重要

生成 SQL 只是开始，能否上线取决于验证。作者把验证分四类：

| 类型 | 检查什么 |
|------|----------|
| **SQL 逻辑验证** | 表/字段是否存在、join 是否合理、聚合层级、时间字段是否选对、过滤条件是否遗漏（可充分利用 Ossie 的 dataset/field/relationship/metric 定义——如 metric 依赖支付时间却被用了创建时间，应被拦下） |
| **强业务规则验证** | 语法看不出的规则：内部账号必须排除、测试门店排除、某类退款订单不进收入、特定业务线只能用特定汇总表 |
| **数据量级验证** | 日活突然比历史均值大十倍、收入比财报差两个数量级 → 给出风险提示（不判绝对对错，但能发现明显异常） |
| **历史问句对比** | 维护已验证问句与 SQL；新 SQL 不要求完全一致，但**必须能解释差异**：为什么换表/换过滤条件/换时间字段/口径更新 |

> 关键句：**AI 系统的质量不应只看一次回答的表面效果，而应看它能否在历史语义中保持一致。**

## 7. 语义层需要持续更新（闭环）

语义不是一次性建成的。三个更新来源：

1. **系统元数据更新 Ossie**：Hive/StarRocks/PostgreSQL 表结构变化、指标平台定义变化 → 新增字段/类型变化/表下线/口径变更都要走**版本管理与校验流程**
2. **历史问句沉淀业务知识**：用户的追问、纠错、确认是语义信号。例："这里的新用户不是注册新用户，是首次支付用户" —— 不应只停留在一次对话里，而应沉淀为业务知识并关联到指标、字段、历史问句与校验规则
3. **用测试集评价效果**：测试集应包含高频问题、复杂 join、易混淆指标、特殊业务规则、枚举值映射、历史口径问题；每次语义模型/提示词/检索策略/SQL 生成逻辑变化后都要跑一遍——否则无法判断系统是变好了，还是只是这次看起来更顺

→ 闭环跑起来后，AI 取数系统才从"一次性问答工具"变成"**持续学习业务语义的系统**"。

## 8. Ossie 的真实价值

> 一句话：**Ossie 的价值不是让 AI 更会写 SQL，而是让 AI 更少误解业务。**

- 把数据集、字段、关系、指标、AI 上下文变成一份**机器可读的语义契约**；
- 让 Hive / StarRocks / PostgreSQL 在语义层被统一描述；
- 让事实表 / 指标表 / 派生指标 / 衍生指标的关系更清楚；
- 让语义定义有机会进入 **Git、校验、评审、转换与自动化流程**。

**但它不替代** Wiki、图 + 向量库、指标治理、数据建模。现实做法是把它放在 AI 取数链路的中间：

- 上游：数仓元数据、指标平台、数据标准、业务文档
- 中间：Ossie 形成结构化语义模型
- 旁边：Wiki 补业务解释，图 + 向量库补关系推理
- 下游：Text-to-SQL、数据分析 Agent、BI、可视化、自动报表
