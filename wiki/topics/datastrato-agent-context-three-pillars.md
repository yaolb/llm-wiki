# Datastrato 2.0：Agent Context 的三重支柱（统一元数据 → 开放语义层 → Ontology）

> 素材分析：微信公众号「DataFun」《全球首发！Datastrato 2.0：统一元数据、开放语义层与 Ontology》（2026-09-16），原文归档于 `raw/datastrato-2-0-agent-context-three-pillars-wechat.md`。
> ⚠️ 来源性质：本篇是 **DACon 2026 北京站演讲预告 + Datastrato 2.0（Gravitino 2.0 企业版）发布稿**，含较多票务与活动宣传。其中的**「Agent Context 三重支柱」框架**是可复用的实质内容，厂商主张与成绩为**自述**，未见第三方验证。

## 概述

文章的问题起点是一句很具体的抱怨：

> 业务部门来问"这个月到底卖了多少钱"，你的数仓里有三张表、两套指标口径，还有一套是上周刚改的规则。
> 过去这事靠数据团队吵一星期，**现在把问题抛给了 Agent——但 Agent 更懵**：数据它都找得到，可它不知道这三个数谁算的对、背后的业务规则是什么、自己能不能照着回答直接去下指令。

由此提出一个判断：当 Agent 从"回答问题"走向"**推理、决策与执行**"，企业最大的瓶颈不再是模型会不会答，而是**它没有可依赖的企业上下文**。Agent 需要的不只是"数据在哪里"，而是三件事：

1. **数据意味着什么**
2. **业务实体如何关联**
3. **行动受哪些规则约束**

## 三重支柱（逐层递进）

Datastrato 创始人兼 CEO 堵俊平（Apache Gravitino 项目发起人，原 LF AI & Data 基金会董事主席）把 Agent 上下文拆成三层：

| 层次 | 支柱 | 承载技术 | 解决 Agent 的什么问题 |
|------|------|----------|----------------------|
| 第一层 | **统一元数据** | Apache Gravitino | 跨云、跨引擎、多模态地把数据资产描述清楚 → "数据在哪、哪些能用" |
| 第二层 | **开放语义层** | 指标 / 维度 / 业务定义跨工具共享 | 把"一个指标多个口径"的语义孤岛钉死 → 不同工具和 Agent 拿到**一致的业务理解** |
| 第三层 | **Ontology** | 业务实体、关系、规则显式建模 | 把自然语言里的业务意图**精确映射到真实数据和操作边界内** |

> 顺序是关键：**先统一元数据，再开放语义，最后 Ontology 收口**——三层衔接，Agent 才能在明确治理边界里把"懂业务"变成"可执行的动作"。

## 更值得记的一点：对"上下文怎么建"的路径纠偏

这可能是全文最有价值的判断。堵俊平指出两条路径各有硬伤：

- **自上而下**（从应用任务出发建语义）：**出价值快**，但容易形成**重复建模、彼此复用的上下文孤岛**——每建一个应用就重搭一遍
- **自下而上**（从元数据治理出发）：底座扎实，但**没法只凭技术结构推导出业务含义**

**推荐的混合路径**：以业务场景牵引建模 → 用统一元数据连接业务概念、数据资产与治理规则 → 靠**业务校验 + Agent 使用反馈**持续迭代。

理由很实在：**上下文会"过期"**。数据漂移、业务规则变化、模型升级都会让旧上下文失效，而**不保鲜的上下文反而会把 Agent 带偏**。

## 产品化：从数据目录到 AI Context Platform

- **Datastrato 2.0（Gravitino 2.0 企业版）** = 融合三重支柱，推动**数据目录（Data Catalog）向 AI Context Platform 演进**
- 开源底座：**Apache Gravitino**——用来先把跨云、跨引擎的元数据底座立起来
- 演讲安排：2026-10-23~24 DACon 2026 北京站主论坛；同场另一位讲师李明皇讲 Agent 如何"每个回答都有据可查"——堵俊平讲的是**更靠前的一步：Agent 开口之前，上下文底座怎么建**

这条线里现在有三篇，构成一个「语义层 / Agent 上下文」主题簇，但**技术路线不同**，值得对照读：

| 篇目 | 路线 | 核心主张 |
|------|------|----------|
| [[从 Arrow 到 Iceberg 到 Polaris 到 Ossie：语义标准化的最后一块拼图]] | **开放标准**（Apache 孵化） | 语义层是五层数据栈演进的最后一层，Ossie 给数据表加"翻译说明书" |

| **本篇（Datastrato 2.0）** | **产品化三层**（元数据 → 语义 → 本体） | 统一元数据是**地基**，开放语义层是**一致性**，Ontology 是**可执行的边界** |

**三者的分歧点**（值得留意）：

- Ossie 路线把**语义层**当作"最后一块拼图"，元数据层由 Polaris 承担
- Datastrato 路线把**统一元数据**（Gravitino）放在**第一层**，语义层居中，Ontology 收口——比 Ossie 多了一个显式的"本体"终点
- 但对"上下文会过期、必须靠反馈迭代保鲜"这一点，**两条路线完全一致**

## 一句话小结

**Agent 的门槛已经从"模型会不会答"前移到"喂给它的上下文底座扎不扎实"**；而上下文不是一个静态资产，是需要持续保鲜的、分层的治理工程。
