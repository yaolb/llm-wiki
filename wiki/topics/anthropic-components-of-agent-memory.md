# Anthropic 的 Agent 记忆实验：Wiki 与原文检索要一起用

> 来源：DataFunTalk《Anthropic重磅公开Agent记忆内幕！》（2026-11-09）对 Anthropic 研究《The components of agent memory》的解读
> 原文：https://mp.weixin.qq.com/s/cpjAuL6FuiLFVWt2lfUK6A
> 一手来源：https://www.anthropic.com/research/components-of-agent-memory（2026-11-06，已核实可访问）
> 原始素材：`raw/anthropic-agent-memory-wiki.md`；**6 张图**见 `raw/assets/anthropic-agent-memory-wiki/`
> **来源性质**：第三方解读稿（DataFunTalk），数据转述自 Anthropic 官方研究。

## 一句话

**只查整理好的 Wiki，不如直接搜原文；两样一起用，效果最好、而且每题还更省 Token。**

## 实验设计

**语料**：软件公司 Stainless 的文件，约 **4.2 亿 Token**（文中称 35 万份企业文件）

**建 Wiki**：Claude **Opus 5** 在 **128 个会话**里逐步搭建——

- 每轮接着前几轮继续，用**共享日志**记录进度
- 探索文件、增补页面、**合并重复内容**
- 有疑问**回原文件核对**
- 产出是**按主题组织、彼此链接**的页面

**评测**：25 道题，指标是「**回答满足了多少评分项**」——一道题可能同时考时间、涉及的人、决策结果，答对两项仍可能漏第三项。

## 核心结果

| 检索方式 | 评分项达成率 |
| --- | --- |
| 只查 Wiki（整理 2 轮） | 13% |
| 只查 Wiki（整理 128 轮） | **48%** |
| 只搜索原文 | **53%** |
| **Wiki + 原文搜索** | **61%** |

**Token**：两样一起用时，每题比只搜原文**少用约 2 万 Token**。

## 为什么 Wiki 单独不够

**根本原因：写下摘要时，你不知道下一位读者会问什么。**

> 「外派员工走单独流程」对大多数员工只是脚注，对来提问的那个人却是整张报销单的关键。

只要那条规则**没写进 Wiki**，即使关键词摆在眼前，Agent 也得回原文找。

### 但 Wiki 让检索变快

- 没有 Wiki 时：搜「酒店报销」→ 读到差旅标准、申请表、答疑、旧通知 → 才知道还该搜「外派」「费用归属」→ 已经读了好几轮无关材料
- 有 Wiki 时：「差旅报销」页**提前串起**「派驻政策」和「费用归属」→ 有几个更准的起点 → 沿链接确定找哪个部门、哪份制度 → 再读原文到具体条款

> **省下的是摸索的那几步。**

## 任务类型决定收益

- **并购题**（必须拼多份文件 + 判断计算）：Wiki **87%** vs 只搜原文 **73%**
- **法律文书测试**（关键词在单份文件内就能定位）：**Wiki 增益不明显**

**判断标准**：

- 「查某份合同的到期日」→ 考**定位**，搜到就能读，Wiki 帮助有限
- 「这家供应商下个月能不能停供」→ 需要把主合同、补充协议、未交付订单、采购记录**连起来**，这才是 Wiki 的主场

## 成本账：省的是答题阶段，不是建库阶段

- 每题少用 2 万 Token 是**答题阶段**的数字
- 前面 128 轮建库 + 后续修订页面**都要花算力**
- **只有同一批资料被反复问，整理的投入才能摊薄**

> 每周换一套材料、每套只查一两次 → **收益要另算**。

## 记错的记忆比漏记更危险

**《宝可梦 红》实验**：

1. Claude 把宝可梦中心记在**月见山东侧**，实际在**西侧**
2. 出来后看自己的笔记，以为已经穿过月见山，继续往前走
3. 跳下**只能单向通过**的台阶，回到来时的路
4. 那次运行里**掉下去三次**，始终没到下一座城

**修复机制叫 dreaming**：

- 在两次会话之间，让 Claude **回看会话记录**，把笔记和当时发生的事对一遍
- 位置纠正后，它知道还得重新进洞，后来抵达华蓝市

### dreaming 的结构（图2 说明）

- **会话记录是只读输入**
- **子 Agent + Orchestrator 分工**整理
- 产出写入**不改动原始输入**的输出记忆

**企业里的对应问题**：一条「外派员工走普通差旅流程」的旧笔记，可能来自某次特批，也可能是 Agent 当时理解错了。

- **会话记录**能解释「为什么这么记」
- **业务原文**才能证明「这条规则适用于谁」

**后台整理该优先盯**：

- 频繁被引用的页面
- 刚被新版本替代的页面
- 已经与原文冲突的页面

> 把每条旧记忆都定期重读一遍，算力花得多，还可能赶不上最急着纠正的那条。

## 哪些能压缩，哪些必须逐字保留

**合同测试（反例）**：让多个 Agent 往**同一张表**填条款 →

- 表格看起来规整，但**摘要漏掉细节**
- **并行写入时有内容被别的 Agent 覆盖**
- 最终覆盖 57 项事实中的 **41 项**

**修正后**：

- 每份合同由**一个 Agent 单独写一页**
- **关键条款保留原句**
- 重建 Wiki 后同一任务覆盖 **57 项（全中）**

> ⚠️ 作者提醒：两处改动是同时生效的，**「保留原句」和「避免覆盖」各自贡献多少，还需要拆开测**。

### 由此得出的分界线

| 类型 | 处理方式 |
| --- | --- |
| 「到哪提交、一般谁审核、相关制度有哪些」 | 适合写成**容易扫一眼**的页面 |
| 「外派是否适用、适用到哪天、超多少金额要另批」 | **可以摘录，但必须同时记原文出处、版本、生效日期、条款位置** |

## 怎么验证这套设计有没有用

**题目设计**：日常问题 + **容易掉坑的题**

- 两位员工住同一家酒店、费用一模一样，一个普通出差、一个外派
- 把**新旧两版规定都放进库**，看它会不会引用已失效的那份

**指标不止「答对没」**：

- 有没有找对**条款**
- 读了多少**无关材料**
- 找不到依据时**会不会交回人工**

## 关键洞察

1. **Wiki 与原文检索是互补，不是替代**：一个给起点与结构，一个保证细节不缺
2. **记忆的价值取决于「问题是否重复」**：一次性语料不值得建 Wiki
3. **摘要必须可追溯**：没有出处、版本、生效日期的摘要，会变成「看似可靠的错误」
4. **记忆需要后台纠错机制**：dreaming 用会话记录校准笔记，但**不能替代业务原文**
5. **压缩与保真是分层的**：流程可摘要，**判定性条款必须逐字 + 溯源**

## 待验证 / 证据边界

- 数据均转述自 Anthropic 官方研究，**未读原文全文**（仅核实页面可访问）
- 「35 万份文件 / 4.2 亿 Token」的统计口径未说明（是否去重、含附件与否）
- 25 道题的**难度分布与评分细则**未公开，48%/53%/61% 的差异是否统计显著未知
- 「每题省 2 万 Token」未包含建库摊销，**不能当作端到端成本结论**
- 合同测试「41/57 → 57/57」是**两处改动同时生效**，归因不完整（作者自己承认）
- 宝可梦实验是**单次演示**，不能证明 dreaming 在通用任务上的效果
- dreaming 的实现细节（触发频率、子 Agent 职责划分、如何避免覆盖）未展开
